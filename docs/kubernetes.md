# Kubernetes deployment and verification

Two manifests are supplied. `deploy/kubernetes.yaml` is the original single-coordinator legacy architecture with three volatile storage pods. `deploy/kubernetes-consensus.yaml` runs three persistent etcd members, four volatile storage pods, and two stateless gateways. The consensus manifest was verified on kind v0.33.0 / Kubernetes v1.37.0 with dynamically provisioned local-path PVCs. Both manifests passed server-side schema validation and live API checks. See [help.md](../help.md) for exact setup/test/cleanup commands.

The consensus data plane uses stable StatefulSet names (`cache-0.cache:8080` etc.) with a fresh process incarnation after restart; pod IPs are not storage identity. Storage registers through leased etcd metadata. Endpoint discovery and DNS alone do not grant ownership. Headless etcd discovery publishes not-ready addresses and starts peers in parallel so initial quorum can form. Each etcd member keeps its own PVC and immutable ordinal/DNS identity. A default StorageClass supporting ReadWriteOnce volumes is required; select and capacity-plan a production class explicitly before deployment. The sample requests 1 GiB per member, not a validated production capacity.

Provide `cache-tokens` Secret in the destination namespace with three distinct CACHE_CLIENT_TOKEN, CACHE_INTERNAL_TOKEN and CACHE_ADMIN_TOKEN values, each at least 16 characters. The verification harness generates disposable random credentials or reuses its existing namespace Secret without printing values. Do not expose internal APIs or the unauthenticated sample etcd ports outside a trusted local network. Provision etcd authentication/mTLS and cache HTTP TLS, restricted service accounts and appropriate network policies before production. These manifests do not perform that provisioning.

Both manifests include startup/readiness/liveness probes and resource requests/limits. Consensus etcd liveness checks local TCP reachability so a temporary quorum loss does not trigger a quorum-health restart loop; readiness checks consensus health. Cache/gateway `/actuator/health` probes currently establish process health, not a linearizable ownership or data-availability guarantee. A ready cache pod can still return 503 during elections or loss of consensus. Treat application readiness improvements as remaining work, and monitor actual authenticated data-plane success.

PDBs permit at most one voluntary etcd disruption (minAvailable 2), at most one storage disruption from four replicas (minAvailable 3), and at most one gateway disruption (minAvailable 1). Preferred anti-affinity allows a single-node test cluster but does not ensure production failure-domain separation. PDBs do not fence stale processes, do not prevent direct pod deletions, and do not make simultaneous node loss safe. The test used direct deletion; it did not validate a node-drain/zone-failure campaign.

The live consensus acceptance suite verified primary pod replacement, changed incarnation and replica repair, scaling storage 4→5→4 with retained reads, rolling gateway restart, and etcd pod replacement retaining the same persistent Raft member ID. It checked reads after each transition, not zero errors throughout the transition. Store bytes remain volatile: losing all copies causes a cache miss; etcd stores pointers/metadata, not cached payloads.

For storage maintenance, change one pod at a time, then wait for the new incarnation, sufficient live owners, successful replica repair and authenticated read probes before touching another. A blind rolling restart of all storage pods is not a validated safe upgrade procedure. Do not scale etcd by simply changing StatefulSet replicas: membership changes require etcd's explicit member-add/remove procedure and a backup/recovery plan. Keep three fixed etcd ordinals in this sample. Gateway rolling restart and storage online scale-out/in were tested; incompatible-version upgrades, full storage rolling restart, storage-driver failure, snapshot/restore, certificate rotation and multi-node failure domains were not.

The harness records non-secret pod/Service/PDB/PVC status, events and bounded pod logs in `target/kubernetes-<mode>/`. By default it deletes the dedicated namespace and PVCs after verification; reclaim behavior depends on the StorageClass. The tested kind local-path class used Delete reclamation. `--keep` retains resources even on failure. Use only disposable cluster credentials and explicit kubeconfig; the tool never changes the current context or touches other namespaces. Delete the dedicated kind cluster after use to remove its local volume data.

Upstream references: [kind cluster/image loading](https://kind.sigs.k8s.io/docs/user/quick-start/) and [Kubernetes StatefulSet identity/storage semantics](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/). Local test results establish only the behavior explicitly recorded above.
